## 1. 结论速览

| 问题 | 结论 |
| --- | --- |
| 现在账户数据存在哪 | `server/data/users.json`、`sessions.json`、`audit.json`，由 [store.mjs](file:///e:/Code/AI/Start/Web/Blog/resume1/server/lib/store.mjs) 的 `JsonStore` 读写 |
| 现在能不能持久化 | 能。原子写（tmp + rename）+ 串行写队列，重启不丢；但**没有唯一约束、没有索引、没有事务、整文件读写** |
| 账户持久化的最短改造面 | 只需改 [auth.mjs](file:///e:/Code/AI/Start/Web/Blog/resume1/server/lib/auth.mjs) 里的 `ensureUsers / login / getSession / logout / audit` 五个函数，外加新增 `server/db/*`。业务路由完全不动 |
| 推荐方案（当前阶段） | **SQLite**：Node 22 内置 `node:sqlite`，零依赖、单文件、有事务和索引，`npm run api` 直接可用 |
| 推荐方案（生产/多实例） | **PostgreSQL + Prisma**：唯一约束、事务、迁移、连接池、可托管备份 |
| 不推荐 | MongoDB（账户需要强关系和唯一约束）、MySQL（除非已有运维体系）、继续纯 JSON（增长后写放大明显） |
| 改造开关 | 新增 `STORAGE_DRIVER=json \| sqlite \| postgres`，默认 `json`，可随时回滚 |

### 2.2 持久化现状：`JsonStore`

[store.mjs](file:///e:/Code/AI/Start/Web/Blog/resume1/server/lib/store.mjs) 的核心行为：

| 能力 | 实现 | 说明 |
| --- | --- | --- |
| 读取 | 进程内 `Map` 缓存 + `readFile` + `JSON.parse` | 解析失败回落到初始值，不报错 |
| 写入 | 先写 `.tmp`，再 `rename` 覆盖 | 崩溃窗口小，但不是事务 |
| 并发 | `update()` 串行队列 + 深拷贝草稿 | 同进程内不会写坏，但**跨进程会互相覆盖** |
| 版本 | `this.version` 自增（仅内存） | 不能跨重启判断版本 |
| 元信息 | `meta()` 返回 size / mtime | 无索引、无查询能力 |

`getStores()` 一次性创建 11 个 store，每个对应一个 JSON 文件：

| store | 文件 | 主要字段 |
| --- | --- | --- |
| `content` | `content.json` | articles / projects / moments / trips / tracks / friends / awards / skills / resources / toolboxGroups / education / research / stats / growthTimeline / profile / siteMeta |
| `users` | `users.json` | `users[]` |
| `sessions` | `sessions.json` | `sessions[]` |
| `guestbook` | `guestbook.json` | `messages[]` |
| `files` | `files.json` | `files[]` / `shares[]` |
| `analytics` | `analytics.json` | `hits[]`（上限 20000）/ `errors[]`（上限 2000） |
| `ai` | `ai.json` | `prompts[]` / `usage[]`（上限 5000）/ `sessions[]` / `cache` / `feedback[]` / `quota` / `models[]` |
| `jobs` | `jobs.json` | `jobs[]`（上限 500） |
| `audit` | `audit.json` | `logs[]`（上限 2000） |
| `settings` | `settings.json` | `profile` / `site` / `updatedAt` |
| `resume` | `resume.json` | `modules[]` / `versions[]` |

补充事实：

- `backupSnapshot()` **排除** `sessions`，避免 sid 哈希随备份外流（`server/lib/store.mjs:115`）。
- 备份文件落在 `server/data/backups/backup-*.json`（`server/routes/system.mjs:25`）。
- 所有写入都经过 `update()`，因此改造时保持「读 → 改 → 写」的语义即可平移。

### 2.3 账户数据现状

**用户表（逻辑结构）**

```json
{
  "users": [
    {
      "id": "u_admin",
      "user": "admin",
      "role": "admin",
      "passwordHash": "salt:hash",
      "createdAt": "2026-01-01T00:00:00.000Z"
    }
  ]
}
```

- 密码：`scrypt(password, salt, 64)`，存储格式 `salt:hash`，校验用 `timingSafeEqual`（[auth.mjs](file:///e:/Code/AI/Start/Web/Blog/resume1/server/lib/auth.mjs#L16-L29)）。
- 启动种子：`ensureUsers()` 在 `users` 为空时按 `ADMIN_USER/ADMIN_PASS`、`EDITOR_USER/EDITOR_PASS` 插入两条账号；口令缺失时 [env.mjs](file:///e:/Code/AI/Start/Web/Blog/resume1/server/lib/env.mjs#L76-L84) 的 `assertSecureConfig()` 直接拒绝启动。
- 角色：`admin`（全部写权限）、`editor`（内容/审核，不可改系统设置与 AI 密钥），由 `ROLE_WRITE` / `ROLE_ADMIN` 判定。

**会话表（逻辑结构）**

```json
{
  "sessions": [
    {
      "id": "sha256(sid)",
      "user": "admin",
      "role": "admin",
      "createdAt": 1767225600000,
      "expiresAt": 1767830400000
    }
  ]
}
```

- Cookie 名 `wyx_session`，HTTPS 下降级为 `__Host-wyx_session`；`HttpOnly` + `SameSite=Lax`（+ `Secure`）。
- 只存 `sha256(sid)`，明文 sid 只在 Cookie 里。
- 登录时清理过期会话，并截断到最近 500 条。
- 双限流：`server/routes/auth.mjs` 按 IP 10 次/10 分钟；`auth.login()` 内再按 IP 8 次/10 分钟；限流桶在内存（`server/lib/http.mjs`）。

**审计表（逻辑结构）**

```json
{
  "logs": [
    { "id": "log_...", "actor": "admin", "action": "auth.login", "target": "session", "before": null, "after": {...}, "ts": "ISO" }
  ]
}
```

- `unshift` 到数组头部，超过 2000 条截断（[auth.mjs](file:///e:/Code/AI/Start/Web/Blog/resume1/server/lib/auth.mjs#L42-L56)）。
- 读取方：`/api/admin/metrics`（`auditEvents` + `recentAudit`）（`server/routes/system.mjs:182`）。**账户相关的 store 依赖点非常集中**，这是迁移成本低的关键。

### 2.4 风险清单（为什么必须上数据库）

| 风险 | 现象 | 后果 |
| --- | --- | --- |
| 无唯一约束 | 同一用户名可被并发写入两次 | 可能出现两个 `admin` |
| 无事务 | `users` 与 `sessions` 分属两个文件 | 改密后旧会话不失效，或半写状态 |
| 整文件读写 | 每次登录都要读全量 `sessions.json` | 数据量上来后 O(n) 放大 |
| 无索引 | 登录是数组 `find` | 10 万会话时登录变慢 |
| 跨进程覆盖 | 多实例 / `npm run api` 双开 | 后写覆盖先写，审计丢失 |
| 无保留策略 | 审计固定截断 2000 条 | 合规审计不可用，无法归档 |
| 无迁移机制 | 字段变更靠手写脚本 | 结构漂移，回滚困难 |

### 2.5 结论

账户数据量小、依赖面窄，**适合作为数据库改造的第一批表**：改动集中在 `auth.mjs` 与 `system.mjs` 的 metrics，业务路由不需要动。

## 3. 需求分析：账户数据到底要什么

| 编号 | 需求 | 对应设计 |
| --- | --- | --- |
| R-01 | 用户名全局唯一 | `users.username UNIQUE` |
| R-02 | 密码只存哈希 | 沿用 `scrypt salt:hash`，DB 字段 `password_hash` |
| R-03 | 会话可查询、可撤销、可过期 | `sessions` 表 + `expires_at` 索引 + `DELETE` 撤销 |
| R-04 | 会话不存明文 | `sessions.id = sha256(sid)` |
| R-05 | 审计可检索、可归档 | `audit_logs` 表 + `ts/actor` 索引，替代 2000 条截断 |
| R-06 | 启动幂等 | `ensureUsers()` 查 `COUNT(*)` 再插入 |
| R-07 | 可迁移、可回滚 | `STORAGE_DRIVER` 开关 + 迁移脚本 |
| R-08 | 可备份 | SQLite `VACUUM INTO` / PG `pg_dump` |
| R-09 | 并发安全 | 事务 + 唯一约束（改密时同事务删会话） |
| R-10 | 最小权限 | DB 文件权限 600 / PG 独立账号 |

## 4. 数据库方案对比

> 评判维度按本项目实际情况：单实例、低并发（个人站）、已有零依赖 Node API、必须能在本机跑通。

| 方案 | 依赖与部署 | 事务 | 并发写 | 索引/查询 | 迁移 | 备份 | 运维成本 | 本机可验证 | 适配结论 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| **JSON 文件（现状）** | 0 依赖 | 无 | 单进程串行 | 无 | 手写脚本 | 复制文件 | 最低 | 是 | 仅够演示，不建议长期 |
| **SQLite（`node:sqlite`）** | Node ≥ 22.5 内置，0 依赖 | 有 | 单写多读（WAL） | 有 | `user_version` / SQL | 复制文件 / `VACUUM INTO` | 低 | 是（本项目 Node 22.16 已验证可用） | **阶段一首选** |
| **SQLite（`better-sqlite3`）** | 原生模块，需编译 | 有 | 同上 | 有 | 同上 | 同上 | 低 | 是 | `node:sqlite` API 不稳定时替换 |
| **PostgreSQL + Prisma** | 需服务 + 2 个 npm 包 | 有（强） | 多实例 | 有（含全文/`pgvector`） | `prisma migrate` | `pg_dump` / 托管快照 | 中 | 需要 Docker 或本机安装 | **阶段三/生产首选** |
| **MySQL + Prisma** | 需服务 + npm 包 | 有 | 多实例 | 有 | `prisma migrate` | `mysqldump` | 中 | 需要 Docker | 已有 MySQL 运维体系时可用 |
| **MongoDB + Mongoose** | 需服务 + npm 包 | 单文档事务（需副本集） | 好 | 有（文档索引） | 无强 schema | `mongodump` | 中 | 需要 Docker | 账户强约束场景不合适 |
| **libSQL / Turso** | 云或本地服务 | 有 | 边缘复制 | 有 | SQL | 平台托管 | 中 | 需账号 | 想「SQLite 语法 + 云托管」时可选 |
| **lowdb** | npm 包 | 无 | 无 | 无 | 无 | 复制文件 | 低 | 是 | 只是更好用的 JSON，不算数据库 |

**关键差异解读**

1. **SQLite 的并发边界**：WAL 模式下「一写多读」。个人站写请求（登录、留言、审核）QPS 很低，完全够用；但**不能多实例共享同一个 `.sqlite` 文件**（网络盘上更不行）。
2. **PostgreSQL 的收益**：唯一约束 + 事务 + 连接池 + 可托管备份；如果后续要全文检索、`pgvector`（AI 检索）、多实例水平扩展，直接受益。
3. **MongoDB 不推荐原因**：账户核心诉求是「唯一 + 强一致 + 关联查询（用户↔会话↔审计）」，这是关系型数据库的主场；文档模型的灵活性在这里反而是负担。
4. **MySQL**：能力足够，但与 PostgreSQL 相比没有明显优势，若团队无既有 MySQL 运维经验，直接用 PG。
5. **libSQL**：语法与 SQLite 基本一致，适合以后想托管；本地阶段没必要引入额外服务。
6. **继续用 JSON 的代价**：数据量小的时候确实简单，但审计要长期保留、账户要唯一约束这两点，JSON 做不到。

## 5. 推荐路线

### 阶段 0（当前，1 天内可完成）
- 保持 `STORAGE_DRIVER=json` 不变，先把本文档与表结构定稿。
- 目的：零风险，随时可回退。

### 阶段 1（账户持久化落地）
- 引入 **SQLite（`node:sqlite`）**，只迁移 `users / sessions / audit_logs` 三张表。
- 交付：`server/db/client.mjs`、`server/db/schema.sql`、`server/db/migrate.mjs`、`server/db/repos/*.mjs`、`scripts/db-import-json.mjs`。
- 验收：登录/登出/会话/审计全部走 SQLite，重启后数据仍在，`npm run check:api` 通过。

### 阶段 3（生产化 / 多实例）

## 6. 数据库设计

### 6.1 账户相关表（阶段 1）

字段命名遵循「DB 用 snake_case，仓库层映射回现有 camelCase」，这样业务代码零改动。

```sql
-- SQLite 版本（PostgreSQL 差异见 6.3）
CREATE TABLE IF NOT EXISTS users (
  id            TEXT PRIMARY KEY,
  username      TEXT NOT NULL UNIQUE,
  role          TEXT NOT NULL CHECK (role IN ('admin', 'editor')),
  password_hash TEXT NOT NULL,
  disabled      INTEGER NOT NULL DEFAULT 0,
  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS sessions (
  id           TEXT PRIMARY KEY,           -- sha256(sid)，绝不存明文
  username     TEXT NOT NULL,
  role         TEXT NOT NULL,
  ip_hash      TEXT,
  user_agent   TEXT,
  created_at   INTEGER NOT NULL,           -- epoch ms
  expires_at   INTEGER NOT NULL,           -- epoch ms
  last_seen_at INTEGER
);
CREATE INDEX IF NOT EXISTS idx_sessions_expires ON sessions (expires_at);
CREATE INDEX IF NOT EXISTS idx_sessions_username ON sessions (username);

CREATE TABLE IF NOT EXISTS audit_logs (
  id          TEXT PRIMARY KEY,
  actor       TEXT NOT NULL,
  action      TEXT NOT NULL,
  target      TEXT,
  before_json TEXT,
  after_json  TEXT,
  ip_hash     TEXT,
  ts          INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_audit_ts ON audit_logs (ts);
CREATE INDEX IF NOT EXISTS idx_audit_actor ON audit_logs (actor);
```

设计说明：

- `users.username` 唯一约束替代「数组 `find`」；插入重复会抛 `SQLITE_CONSTRAINT_UNIQUE`，在路由层映射为 409。
- `sessions.id` 直接存 `sha256(sid)`，与 [auth.mjs](file:///e:/Code/AI/Start/Web/Blog/resume1/server/lib/auth.mjs#L72) 的 `sessionKey()` 一致，不需要额外列。
- 会话过期用 `expires_at`（整数毫秒），与现有 `Date.now()` 逻辑天然兼容。
- `audit_logs` 不再截断 2000 条；保留策略交给 TTL 任务（见第 12 节）。
- 时间统一用 **epoch 毫秒整数**，避免 SQLite 没有时区类型的问题。

### 6.2 字段映射（代码视角）

| 现有代码字段 | DB 列 | 转换 |
| --- | --- | --- |
| `account.user` | `users.username` | 直接 |
| `account.passwordHash` | `users.password_hash` | 直接 |
| `account.createdAt`（ISO） | `users.created_at`（ms） | `Date.parse()` / `new Date(ms).toISOString()` |
| `session.id` | `sessions.id` | 直接（已是 `sha256(sid)`） |
| `session.expiresAt`（ms） | `sessions.expires_at`（ms） | 直接 |
| `log.ts`（ISO） | `audit_logs.ts`（ms） | 同上 |
| `log.before` / `log.after` | `before_json` / `after_json` | `JSON.stringify` / `JSON.parse` |

### 6.3 PostgreSQL 差异

```sql
CREATE TABLE users (
  id            TEXT PRIMARY KEY,
  username      TEXT NOT NULL UNIQUE,
  role          TEXT NOT NULL CHECK (role IN ('admin','editor')),
  password_hash TEXT NOT NULL,
  disabled      BOOLEAN NOT NULL DEFAULT FALSE,
  created_at    BIGINT NOT NULL,
  updated_at    BIGINT NOT NULL
);

CREATE TABLE sessions (
  id           TEXT PRIMARY KEY,
  username     TEXT NOT NULL REFERENCES users(username) ON DELETE CASCADE,
  role         TEXT NOT NULL,
  ip_hash      TEXT,
  user_agent   TEXT,
  created_at   BIGINT NOT NULL,
  expires_at   BIGINT NOT NULL,
  last_seen_at BIGINT
);
CREATE INDEX sessions_expires_idx ON sessions (expires_at);

CREATE TABLE audit_logs (
  id          TEXT PRIMARY KEY,
  actor       TEXT NOT NULL,
  action      TEXT NOT NULL,
  target      TEXT,
  before_json JSONB,
  after_json  JSONB,
  ip_hash     TEXT,
  ts          BIGINT NOT NULL
);
CREATE INDEX audit_ts_idx ON audit_logs (ts DESC);
```

注意：`sessions.username` 外键指向 `users.username` 需要 `users.username` 有唯一约束（已满足）。如果希望改用户名不影响会话，改成指向 `users.id` 并把 `user_id` 写进会话表。

### 6.4 阶段 2 预留结构（内容域）

```sql
CREATE TABLE documents (
  domain     TEXT NOT NULL,
  id         TEXT NOT NULL,
  data_json  TEXT NOT NULL,
  version    INTEGER NOT NULL DEFAULT 1,
  status     TEXT NOT NULL DEFAULT 'published',
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  PRIMARY KEY (domain, id)
);
CREATE INDEX documents_domain_status ON documents (domain, status);

CREATE TABLE settings (

```

对应的仓储契约保持 `read() / update(mutator)`，内部用「读一个 domain 的所有行 → 深拷贝 → 事务写回」，接口层完全不改。

## 7. 代码对接改造方案

### 7.1 设计原则

1. **不动路由、不动前端**：`/api/auth/*`、`/api/admin/*` 的请求/响应结构保持原样。
2. **保留 `getStores()` 契约**：其余 8 个 store 继续走 JSON，逐步迁移。
3. **驱动开关**：`STORAGE_DRIVER=json | sqlite | postgres`，默认 `json`，出问题一条环境变量回退。
4. **仓储层负责映射**：DB 行 ↔ 业务对象（`snake_case` ↔ `camelCase`），上层无感知。

### 7.2 新增文件清单

```
server/
├─ db/
│  ├─ client.mjs          # 连接（sqlite / postgres）
│  ├─ schema.sql          # 账户三张表
│  ├─ migrate.mjs         # 建库/建表/版本号
```

### 7.3 连接层（SQLite）

`server/db/client.mjs`

```js
import { DatabaseSync } from 'node:sqlite'
import { mkdirSync } from 'node:fs'
import { resolve } from 'node:path'
import { env } from '../lib/env.mjs'

let db = null

export function getDb() {
  if (db) return db
  const file = resolve(env.dataDir, env.dbFile)
  mkdirSync(env.dataDir, { recursive: true })
  db = new DatabaseSync(file)
  // WAL：一写多读；busy_timeout 让并发写排队而不是直接报错
  db.exec('PRAGMA journal_mode = WAL')
  db.exec('PRAGMA foreign_keys = ON')
  db.exec('PRAGMA busy_timeout = 5000')
  return db
}

export function closeDb() {
  if (db) db.close()
  db = null
}
```

```js
import { readFileSync } from 'node:fs'
import { dirname, resolve } from 'node:path'
import { fileURLToPath } from 'node:url'
import { getDb, closeDb } from './client.mjs'

const here = dirname(fileURLToPath(import.meta.url))
const SCHEMA_VERSION = 1

function currentVersion(db) {
  try {
    const row = db.prepare('PRAGMA user_version').get()
    return Number(row?.user_version ?? 0)
  } catch {
    return 0
  }
}

function migrate() {
  const db = getDb()
  const version = currentVersion(db)
  if (version >= SCHEMA_VERSION) {
    console.log(`[db] already at version ${version}`)
    closeDb()
    return
  }
  db.exec(readFileSync(resolve(here, 'schema.sql'), 'utf8'))
  db.exec(`PRAGMA user_version = ${SCHEMA_VERSION}`)
  console.log(`[db] migrated ${version} -> ${SCHEMA_VERSION}`)
  closeDb()
}

migrate()
```

> `PRAGMA user_version` 的读取在不同 Node 版本上略有差异；`currentVersion()` 用 `try/catch` 兜底，读不到就当作 0（会重跑一次建表语句，`IF NOT EXISTS` 保证幂等）。

### 步骤 4：导入现有 JSON 数据（如果已有 `server/data/*.json`）

`scripts/db-import-json.mjs` 核心逻辑：

```js
import { readFile, writeFile } from 'node:fs/promises'
import { existsSync } from 'node:fs'
import { resolve } from 'node:path'
import { getDb } from '../server/db/client.mjs'
import { env } from '../server/lib/env.mjs'

const readJson = async (name, fallback) => {
  const file = resolve(env.dataDir, name)
  if (!existsSync(file)) return fallback
  return JSON.parse(await readFile(file, 'utf8'))
}

async function main() {
  const db = getDb()
  const users = (await readJson('users.json', { users: [] })).users
  const sessions = (await readJson('sessions.json', { sessions: [] })).sessions
  const logs = (await readJson('audit.json', { logs: [] })).logs

  const insertUser = db.prepare(
    'INSERT OR IGNORE INTO users (id, username, role, password_hash, created_at, updated_at) VALUES (?, ?, ?, ?, ?, ?)',
  )
  for (const u of users) {
    const ts = Date.parse(u.createdAt ?? '') || Date.now()
    insertUser.run(u.id, u.user, u.role, u.passwordHash, ts, ts)
  }

  const insertSession = db.prepare(
    'INSERT OR IGNORE INTO sessions (id, username, role, created_at, expires_at) VALUES (?, ?, ?, ?, ?)',
  )
  for (const s of sessions) insertSession.run(s.id, s.user, s.role, s.createdAt, s.expiresAt)

  const insertLog = db.prepare(
    'INSERT OR IGNORE INTO audit_logs (id, actor, action, target, before_json, after_json, ts) VALUES (?, ?, ?, ?, ?, ?, ?)',
  )
  for (const l of logs) {
    insertLog.run(l.id, l.actor, l.action, l.target ?? null, JSON.stringify(l.before), JSON.stringify(l.after), Date.parse(l.ts))
  }

  console.log(`[db] imported users=${users.length} sessions=${sessions.length} logs=${logs.length}`)

  // 导入成功后把原文件改名存档，避免下次启动又被 JSON 读取
  const stamp = new Date().toISOString().replace(/[:.]/g, '-')
  for (const name of ['users.json', 'sessions.json', 'audit.json']) {
    const from = resolve(env.dataDir, name)
    if (existsSync(from)) await writeFile(`${from}.bak-${stamp}`, await readFile(from))
  }
}

main()
```


> 脚本只做「复制」，不删除原 JSON；确认 DB 内数据正确后再手工归档。

```js
}
```

`sessionsRepo` / `auditRepo` 同理，方法签名与 7.4 小节一致（`create / findActive / deleteByHash / deleteExpired / pruneToLimit` 与 `add / list / count`），内部换 Prisma 调用。这样 `auth.mjs` 只需要按 `env.storageDriver` 选择 repo 实例：

```js
const repos = env.storageDriver === 'postgres'
  ? await import('../db/repos/pg/index.mjs')
  : await import('../db/repos/sqlite/index.mjs')
```

### 步骤 6：导入现有 JSON

把 `db-import-json.mjs` 里的 `DatabaseSync` 调用替换为 Prisma 的 `createMany`：

```js
await prisma.user.createMany({ data: users.map(toRow), skipDuplicates: true })
await prisma.session.createMany({ data: sessions.map(toRow), skipDuplicates: true })
await prisma.auditLog.createMany({ data: logs.map(toRow), skipDuplicates: true })
```

> 注意 `BigInt` 列不能直接 `JSON.stringify`；Prisma 返回的 `BigInt` 要用 `Number()` 转换后再输出。

## 12. 运维与安全

### 12.1 定期任务

| 任务 | 频率 | 命令/实现 |
| --- | --- | --- |
| 清理过期会话 | 每小时 | `sessionsRepo.deleteExpired()`（可挂在 `server/index.mjs` 的 `setInterval`） |
| 审计归档 | 每月 | 把 90 天前的 `audit_logs` 导出为 JSON 后删除 |
| 数据库备份 | 每天 | SQLite `VACUUM INTO` / PG `pg_dump` |
| 体积巡检 | 每周 | `PRAGMA page_count` × `page_size`；PG 用 `pg_database_size()` |
| 慢查询 | 按需 | SQLite `PRAGMA optimize`；PG `pg_stat_statements` |

### 12.2 安全要点

1. **文件权限**：SQLite 文件与目录仅服务账号可读写（Linux `chmod 600`；Windows 用 ACL 限制）。
2. **最小权限**：PostgreSQL 单独建应用账号，只授予 `SELECT/INSERT/UPDATE/DELETE`，不授予 `SUPERUSER`。
3. **连接加密**：PG 生产强制 `sslmode=require`。
4. **口令不落地明文**：继续使用 `scrypt salt:hash`；不要为了「兼容」加明文列。
5. **会话不存明文**：`sessions.id` 永远是 `sha256(sid)`。
6. **审计不可篡改**：应用账号不要给 `UPDATE/DELETE` 权限（或只给 `INSERT/SELECT`），归档用独立账号。
7. **备份加密**：备份文件用 `age` / `gpg` 加密后再传对象存储。
8. **限流与配额仍在内存**：多实例时要换 Redis；单实例 SQLite 阶段可保留现状。

### 12.3 监控指标

- 登录成功率 / 失败率（来自 `audit_logs.action`）。
- 会话数量与平均存活时长（`COUNT(*)` / `AVG(expires_at - created_at)`）。
- DB 文件体积、WAL 体积（SQLite）。
- 备份成功率（`server/data/backups/` 目录数量与时间戳）。
- API `/healthz`、`/readyz` 已有探针，可继续用。

## 13. 常见问题

**Q1：`node:sqlite` 启动时打印 `ExperimentalWarning`，要处理吗？**
A：可以忽略。若要彻底消除，用 `better-sqlite3`（API 基本一致：`prepare().run/get/all`、`exec`、事务用 `db.transaction(fn)`），或升级到 API 稳定的 Node 版本。

**Q2：Node 版本低于 22.5 怎么办？**
A：`npm i better-sqlite3`，把 `DatabaseSync` 替换为 `better-sqlite3` 的 `new Database(file)`；`PRAGMA` 写法一致。

**Q3：SQLite 报 `SQLITE_BUSY`？**
A：确认已开 `PRAGMA busy_timeout = 5000`；不要两个进程同时写同一个文件；WAL 模式下读不会阻塞写。

**Q4：能不能把 `server/data/*.json` 全部删掉？**
A：**不能**。除账户三表外，内容/留言/文件/埋点/AI 仍在 JSON；只删账户三表对应文件即可（先备份）。

**Q5：改密后旧会话为什么还活着？**
A：需要「改密 + 删会话」同事务。按 7.7 小节实现；当前 `seed` 不会自动撤销会话。

**Q6：`ensureUsers()` 会不会每次启动重复插入？**
A：DB 分支先 `COUNT(*)`，非 0 直接返回；同时 `users.username` 有唯一约束，双保险。

**Q7：备份时能继续写吗？**
A：SQLite 用 `VACUUM INTO` 可以在线备份；直接 `Copy-Item` 文件必须停写，否则可能拿到不一致状态（WAL 还包含未落盘数据）。

**Q8：以后想上多实例，SQLite 还能用吗？**
A：不能共享同一个 `.sqlite` 文件。多实例请切 PostgreSQL（阶段 3），或每个实例独立 DB + 只读副本（不推荐）。

**Q9：Prisma 的 `BigInt` 序列化报错？**
A：`JSON.stringify` 不支持 `BigInt`。在仓储层统一 `Number()` 转换，或全局配置 `BigInt.prototype.toJSON`。

**Q10：迁移后 `npm run api` 起不来，提示口令问题？**
A：`assertSecureConfig()` 拒绝空口令/`change-me`。检查 `.env` 的 `ADMIN_PASS` / `EDITOR_PASS` 是否至少 8 位。
